# ADR-0001 — Corpus manifest schema (F1) and the KOBER handshake surface (F0.3)

- **Date:** 2026-08-25 (Session 2)
- **Status:** accepted
- **Scope:** every synthetic corpus produced by `engine/` (F1: "Every synthetic corpus carries a
  manifest"). Manifests for non-synthetic corpora (F4.1 natural language, F4.2 human glossolalia,
  F4.3 contested/quarantine) are **not** decided here; the `origin` field below reserves room for
  them and a later ADR decides their extra provenance fields.

## Context

F1 names the mandatory manifest fields: generator ID + version, full config, seed, commanded
statistics, achieved statistics, tolerance verdict, content hash. Four other rules shape the schema:

- **F5** — a corpus counts only after achieved statistics match commanded statistics within stated
  tolerance, verified per corpus. Prior art independently motivates this: S-0001 (Nair 2026) Table 2
  shows a generator achieving Zipf −0.97 against a commanded −1.46 — a commanded-only manifest would
  have recorded a target the corpus does not have. The schema therefore carries **both** commanded and
  achieved statistics and a per-statistic verdict.
- **F6** — every result records engine commit SHA, seed(s), config hash, uncertainty. A manifest is
  the carrier of exactly those fields for its corpus, so the config hash must be computable
  identically on any platform from the manifest alone.
- **ADR-0000 §4** — LF pinned repo-wide so that digests over committed text are stable. The content
  hash below is defined over a byte format that is LF-only by construction.
- **F0.3** — the manifest is the KOBER handshake surface: KOBER's Phase-3 battery (its P3.3 blind
  validation fails "scrambled/decoy assignments") may someday consume FRIEDMAN corpora as decoy
  populations. Interface, not dependency.
- **F3.2** — calibration runs over corpus size *and* per-document length distribution, so a corpus is
  a sequence of documents, not one token stream, and the manifest must say how many of each.

## Options considered

1. **JSON** (I-JSON subset), hashed via the JSON Canonicalization Scheme (JCS, RFC 8785 — S-0004).
2. **TOML** — Rust-native (Cargo), very readable for flat config.
3. **YAML** — readable, widely used for experiment configs.

Evaluation (engineering judgment, not scholarship):

| Need | JSON + JCS | TOML | YAML |
|---|---|---|---|
| Published canonical byte form for hashing (F6) | yes — RFC 8785 fixes whitespace, key order, number and string serialization, UTF-8 (S-0004 §3.2.1–3.2.4) | none standardized; a repo-local canonical form would have to be invented and maintained | none standardized; same problem |
| Read/write on both F10 tiers without extra dependencies | Rust `serde_json` (to be confirmed at F0.4 per F7); Python stdlib `json` | needs a crate on one side and a third-party module on the other | needs third-party libraries on both sides |
| Nested per-statistic records (value + tolerance + CI) | natural | arrays-of-tables are awkward and easy to mis-nest | natural |
| Typing hazards | I-JSON forbids NaN/Infinity and duplicate keys — an *undefined* statistic must be written as an explicit `null` with a reason (below) | strict typing | implicit typing is parser-dependent; a hash over "the same" document can differ by parser |

## Decision

### D1 — Format

Manifests are **JSON**, restricted to the I-JSON subset required by RFC 8785 (no NaN/Infinity, no
duplicate keys, numbers are IEEE 754 doubles or integers within double range). One manifest per
corpus, file name `manifest.json`.

On-disk form: UTF-8, no BOM, 2-space indent, object keys sorted per JCS order, single trailing LF.
This is a *presentation* rule so that regenerated manifests are byte-identical and `git diff` is
meaningful; it is **not** the hashing form. (Only hashes are canonicalized — see D5.)

### D2 — Layout

```
corpora/<corpus_id>/manifest.json
corpora/<corpus_id>/corpus.txt
```

`corpus_id` = `<generator.id>-v<generator.version>-<config_hash[0:12]>-s<seed>`; example:
`markov-v1.0.0-22cdc154338b-s7`. It is a pure function of (generator, config, seed), so two corpora
with the same id must be byte-identical (F6) — that is a testable engine invariant, not a convention.

Manifests are always committed. Whether `corpus.txt` is committed or regenerated on demand is a
size question decided at F0.4 with the scaffold, once real sizes exist (F7: measure, don't assume);
the manifest's `content_hash` makes a regenerated corpus verifiable either way.

### D3 — Corpus byte format `friedman-tokens/1`

`corpus.txt` is: UTF-8, no BOM; **one document per line**; tokens separated by exactly one U+0020;
no leading or trailing spaces on a line; **every** line, including the last, terminated by exactly
one U+000A; no empty lines; no U+000D anywhere. A token is a non-empty string containing no
whitespace code point (U+0009, U+000A, U+000D, U+0020). Documents are addressed by 0-based line
index; there are no in-band ids.

The format is LF-only by construction, so "SHA-256 over LF-normalized bytes" (ADR-0000 §4) and
"SHA-256 over the file's exact bytes" coincide.

### D4 — Schema `friedman-manifest/1`

Top-level object, all fields required unless marked optional:

| Field | Type | Meaning |
|---|---|---|
| `manifest_schema` | string | exactly `"friedman-manifest/1"` |
| `corpus_id` | string | per D2 |
| `origin` | string | `"synthetic"` for everything this ADR covers; `"natural"` and `"quarantine"` reserved for the F4 ADR |
| `generator` | object | `id` (string, snake_case), `version` (string, semver), `rng` (string naming the RNG algorithm and how sub-streams derive from `seed`; **any change to the RNG or derivation bumps `version`**) |
| `engine_commit` | string | 40-hex git SHA of `engine/` that produced the corpus (F6) |
| `seed` | integer | single master seed, unsigned 64-bit range; generators derive all sub-streams from it deterministically per `generator.rng` |
| `config` | object | the generator's **full** configuration, every dial, no defaults elided (F1 "full config") |
| `config_hash` | string | SHA-256 hex (lowercase) of JCS(`config`) — D5 |
| `ground_truth` | object | `label` (string; `"mechanism"` for every synthetic corpus — never anything else, because the label derives from the generative process, F1), `family` (string, = `generator.id`), `derivation` (string, `"by-construction"`) |
| `corpus` | object | `file` (`"corpus.txt"`), `format` (`"friedman-tokens/1"`), `content_hash` (SHA-256 hex over the file's exact bytes), `n_documents`, `n_tokens`, `n_types` (integers), `doc_length` (`min`, `max`, `mean` over tokens per document) |
| `commanded` | object | map statistic-key → `{ "value": V, "tolerance": T }` — the dials the generator was **told** to hit, in the shared commanded-statistics vocabulary (F2.2) |
| `achieved` | object | map statistic-key → `{ "value": V or null, "estimator": string, "ci95": [lo, hi] or null, "reason": string (required iff value is null) }` — what the engine **measured** on `corpus.txt`; may contain keys not in `commanded` |
| `fidelity` | object | `per_statistic` (map statistic-key → `"PASS"` or `"FAIL"` for every key in `commanded`), `verdict` (`"PASS"` iff every per-statistic verdict is PASS, else `"FAIL"`) — the F5 verdict |
| `notes` | string, optional | free text; never load-bearing |

Deliberately absent: **wall-clock timestamps**. A regenerated manifest must be byte-identical to
the original; time of creation is recoverable from git and would only break that invariant.

Tolerance forms: `{"abs": a}` (PASS iff |achieved − commanded| ≤ a), `{"rel": r}` (PASS iff
|achieved − commanded| ≤ r·|commanded|), `{"exact": true}` (PASS iff equal; for categorical dials
such as an MI-decay class). The verdict compares the **point estimate**; `ci95`, when present, is
reported alongside and does not enter the verdict (keeps the F5 rule pre-declared and simple; if a
CI-aware rule is ever wanted it is a new schema version by ADR, never a silent change). A commanded
key that is missing from `achieved`, or whose achieved value is `null`, is FAIL.

Statistic keys are snake_case identifiers drawn from a registry that lives as code in `engine/`
(enumerated by the F2.2 / F3.1 ADRs). The initial vocabulary named by the constitution is
`entropy_rate`, `zipf_slope`, `morphology_inventory`, `positional_constraints`, `mi_decay_class`;
this ADR fixes the *shape* of entries, not the list.

### D5 — Hashing

Every hash in a manifest is SHA-256, lowercase hex.

- `config_hash` = SHA-256 over the **JCS canonical form** of `config` (RFC 8785, S-0004): no
  inter-token whitespace (§3.2.1); object properties sorted recursively by UTF-16 code units, arrays
  kept in order (§3.2.3); numbers serialized per ECMAScript `Number.prototype.toString`
  (shortest round-trip, §3.2.2.3; NaN/Infinity are errors); UTF-8 output (§3.2.4).
- `content_hash` = SHA-256 over the exact bytes of `corpus.txt` (D3).

Consequence for the engine: it needs a JCS-conformant serializer. Whether that is a crate or an
in-repo implementation with RFC 8785 Appendix B number-vectors as tests is chosen at F0.4 after
checking what exists (F7). Nothing in this ADR depends on which.

### D6 — Golden example (hand-computed; a future engine test must reproduce it)

Corpus (`corpus.txt`, 12 bytes: `62 61 20 6b 61 20 62 61 0a 6b 61 0a`):

```
ba ka ba
ka
```

Config as authored, and its JCS form (57 bytes, note the key order):

```
{"order": 1, "transition_bias": 0.75, "alphabet": ["ba", "ka"]}
{"alphabet":["ba","ka"],"order":1,"transition_bias":0.75}
```

- `content_hash` = `8d106b97f8396631fa7e3f0a597622291ec6c773bd1628a82d44fc0c38ec75fd`
- `config_hash`  = `22cdc154338b0b3c5aa84e767452853343cdebf204e84595aaa2c7feed0cdc33`
- `corpus_id`    = `markov-v1.0.0-22cdc154338b-s7` (seed 7)

Both digests were computed in Session 2 with `sha256sum` over exactly those bytes; the JCS form was
produced by hand from the §3.2 rules and cross-checked with Python's
`json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`, which coincides with
JCS for this input (ASCII keys, short-integer and short-decimal numbers only — the general case
does **not** coincide, which is why the engine needs a real JCS serializer).

Illustrative manifest (values other than the three digests are placeholders for shape only; they
are not measurements and enter no register):

### D7 — The KOBER handshake surface

What KOBER may consume, and all it may consume: a directory `corpora/<corpus_id>/` holding
`manifest.json` (schema `friedman-manifest/1`) and `corpus.txt` (format `friedman-tokens/1`). The
fields a decoy consumer needs are `ground_truth.label` (always `"mechanism"` for synthetic corpora),
`ground_truth.family`, `corpus.format`, `corpus.content_hash` (to pin what was copied), and
`fidelity.verdict` (a consumer should refuse FAIL corpora, F5). KOBER copies by content hash into
its own provenance-tracked sources under its own rules; it never imports FRIEDMAN code, and FRIEDMAN
never imports KOBER data except through the F4 quarantine path already prescribed by the
constitution. Schema evolution: a new manifest schema is a new version string; consumers pin the
string they understand. Neither program blocks the other (F0.3).

## Consequences

- F0.3 exit criterion satisfied by this ADR; the engine-side data types, JCS serializer choice,
  and corpus-commit policy are F0.4 scaffold decisions.
- Every future generator module (F2.1) must declare: `generator.id`, semver `version`, the `rng`
  string, the full `config` shape, and which statistic keys it can be commanded on.
- Golden D6 becomes an engine test at the first opportunity; if the engine ever disagrees with it,
  the engine is wrong until proven otherwise (the digests are over fixed bytes).
- Downgrade path: a manifest whose `fidelity.verdict` is FAIL is not a counted corpus (F5) but is
  still a **finding** — it is kept, not deleted.
- RFC 8785 recorded as S-0004 (retrieved this session, SHA-256 pinned, copy not committed).
